# Contributing to eaa-kit

**The smallest valid contribution: a Bronze jurisdiction pack for one country — about 2 files and one evening, with no knowledge of the engine required.**

If your country is missing from the [support matrix](README.md#jurisdiction-support-matrix), that is the contribution we most want, and you are better placed to make it than any maintainer. You know how your language phrases these things and which authority people actually complain to. We do not.

---

## Set up (one step)

```bash
git clone https://github.com/rpops101/eaa-kit
cd eaa-kit
npm install && npm test
```

Tests should be green immediately. If they are not, that is a bug in this repository — [open an issue](../../issues/new) and we will fix it, because a broken first run is our problem, not yours.

There is a devcontainer, so **Code → Codespaces → Create codespace** also works with nothing installed locally.

## Contribution unit 1: a jurisdiction pack

### What it is

A directory of **data** — no code — that tells eaa-kit how an accessibility statement reads in your country:

```
packages/packs/packs/pt/
├── pack.yaml            # the law, the enforcement body, the languages
├── strings.pt.yaml      # the translation
├── fixture/             # a fake project the tests render (scaffolded for you)
└── snapshots/           # the expected output (generated by a command)
```

### How to make one

```bash
npx eaa-kit contrib scaffold-pack --country pt
```

That writes the whole skeleton, including a `TODO.md` checklist. Then:

1. **Fill in `pack.yaml`.** The national law transposing Directive (EU) 2019/882, and the market surveillance authority a user would complain to. Every claim needs an official source URL in `legal.sources` — that is how a reviewer who does not read your language verifies your pack.
2. **Translate `strings.<lang>.yaml`.** Keys stay, text changes. Delete any key you want left in English; unset keys fall back to English, so a partial translation is valid. Prefer the wording your national authority already uses over a literal translation.
3. **Check your work.**
   ```bash
   npx eaa-kit validate-pack packages/packs/packs/pt
   ```
   This is the same code CI runs, so green locally means green in CI. It lists exactly what remains — an unfinished scaffold fails until every `TODO` is gone.
4. **Read the rendered statement.** You are the first person who can judge whether it sounds like a real statement in your language:
   ```bash
   npx eaa-kit render statement --config packages/packs/packs/pt/fixture/config.yaml --jurisdiction pt --lang pt
   ```
5. **Commit the snapshots** so future changes to the engine can never silently alter your country's statement:
   ```bash
   npm run update-snapshots -w @eaa-kit/packs -- pt
   ```
6. **Add yourself** to `maintainers` in `pack.yaml` and to [CODEOWNERS](.github/CODEOWNERS). You then get review standing on your own jurisdiction — nobody changes your country's wording without you.

### What reviewers check

Almost nothing, by design. The schema and the snapshot tests do the mechanical review (REQ-PACK-2), and CI posts your rendered statement as an artifact so a human reads the *output*, not a diff. What a human looks at:

- Do the source URLs support what `pack.yaml` claims?
- Does the translation read naturally to a native speaker?

That is it. We do not style-review; CI formats code automatically.

### The quality scale

Objective and self-checkable, so you know when you are done:

| | Requirements |
| --- | --- |
| 🥉 **Bronze** | Statement renders in one language; `pack.yaml` complete with sources |
| 🥈 **Silver** | + every official language of the state, + enforcement body verified against an official source with `enforcement.verified` set |
| 🥇 **Gold** | + DOCX template, + translation reviewed by a second native speaker |

Bronze is a complete, mergeable contribution. Start there.

## Contribution unit 2: an evidence reader

Support a tool eaa-kit does not read yet — Playwright's `ariaSnapshot`, WAVE, IBM Equal Access, your in-house checker:

```bash
npx eaa-kit contrib scaffold-reader --name wave
```

You get the module and its test, both commented with what to fill in. A reader is one file implementing `detect()` and `read()`; it never touches conformance computation or rendering. Save a **real** report from the tool as the fixture — real output catches shapes hand-written JSON never will. See [docs/writing-a-reader.md](docs/writing-a-reader.md).

The one hard rule: `detect()` must be strict. A reader that claims another tool's file silently mis-parses somebody's compliance evidence. eaa-kit refuses to guess, and so must your reader.

## Contribution unit 3: translations of the tool itself

The CLI and the shared artifact strings use the same i18n layer packs use ([`packages/core/data/strings/`](packages/core/data/strings)). Adding `strings/nl.yaml` translates eaa-kit itself into Dutch. Pure data, no build step.

WCAG criterion *names* are separately translatable per pack under a `criteria:` key — see [`packs/de/strings.de.yaml`](packages/packs/packs/de/strings.de.yaml) for a worked example. Translating those for your language is a well-scoped afternoon.

## Contribution unit 4: CI recipes

A documented, tested recipe for GitLab CI, CircleCI, Jenkins, Azure Pipelines or Woodpecker is a genuinely useful contribution and lives entirely in [docs/recipes/](docs/recipes/).

## Contribution unit 5: the engine

Core work is welcome too — see issues labelled `core`. Read [docs/architecture.md](docs/architecture.md) first. Core changes need tests, and coverage on `@eaa-kit/core` must stay at or above 90%.

## Ground rules

### Legal accuracy

This tool produces documents with legal weight in a regime with real penalties. So:

- **Cite your sources.** Official government or legislature domains.
- **Open every link before you cite it.** `node scripts/check-pack-links.mjs xx`
  tells you a URL resolves; it cannot tell you it points at the right body.
  One of the launch packs shipped a link to a cable manufacturer that
  happened to share an acronym with the German accessibility authority.
- **Be conservative.** When unsure whether wording is required or optional, include it and say it is included.
- **Never remove the draft watermark machinery.** The disclaimer and the "reviewed by" requirement are liability controls, not decoration.
- **We are not lawyers, and neither is the tool.** eaa-kit generates drafts for human review. Keep language in every artifact consistent with that.

### AI assistance: disclose it

Using an AI assistant is fine, including for translations and boilerplate. Two requirements:

1. **Say so in the pull request.** The template has a checkbox. "Translation drafted with an LLM, reviewed by me as a native speaker" is a perfectly good disclosure.
2. **You must be able to stand behind it.** For a translation, that means you actually speak the language. For a legal reference, that means you opened the source and read it. Machine-translated legal text nobody verified is worse than no pack at all — it looks authoritative and is wrong, in a document whose whole purpose is being correct.

Pull requests that are visibly unreviewed model output get closed with a pointer to this section. This policy exists from day one so it never has to be a reaction to anyone in particular.

### Commits and pull requests

- Branch from `main`, one logical change per pull request.
- Run `npm test` before pushing. `npm run format` handles style — never hand-format for the reviewer's sake.
- Describe *why*, not only *what*. For packs, link your sources.
- Draft pull requests are welcome. Push something incomplete and ask; that is not an imposition.

### Getting help

Open the pull request early, or [an issue](../../issues/new/choose), or a [discussion](../../discussions). **A maintainer replies to every first-time contributor within 24 hours** ([MAINTAINERS.md](MAINTAINERS.md)). If you have been waiting longer, ping the thread — you are not being a nuisance, we dropped it.

Questions like "is this even the right approach?" are good questions. Ask them before spending the evening.

## Code of conduct

Be decent. Assume good faith. Accessibility work attracts people who have been on the receiving end of software that ignored them; that perspective is the point, not an inconvenience.

Report problems to the maintainers listed in [MAINTAINERS.md](MAINTAINERS.md).
